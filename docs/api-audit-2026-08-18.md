# API 監査記録（2026-08-18）

> 本ドキュメントは、`apps/api` の公開エンドポイントを対象とした静的監査（ソースコード・ドキュメント・設定ファイルの精査）の記録です。
> 監査対象は **コミット済みソース + 作業ツリー（未コミット変更を含む）** の現状です。ユーザーにより、**事前存在の未コミット API 作業ツリー変更は本監査・改善の対象として統合が明示的に承認**されています。
> ただし、**作業ツリーのソースは監査対象であっても、それが「本番稼働中の挙動」の証拠ではありません**。デプロイ状態は未検証です。
> リリース判断にはランタイムテスト（§13）と、未コミット作業ツリーのオーナー判断が必要です。
>
> **Gate 2 承認・Phase 3 適用・Phase 4 検証**: F-01 / F-03 / F-04 / F-06 の修正は Gate 2 で承認され Phase 3 で適用済み（§14）。Phase 4 で Docker コンテナ内の検証が実行され、F-10 / F-11 も解決済み（§15 / §16 / §17）。ただし**デプロイ実行時・DB 統合のテストは実施していない**。

## 1. スコープ・方法・バージョン基準

### 1.1 スコープ

- 対象: `apps/api`（Hono REST API）の公開エンドポイント 45 本
- 対象外: `apps/bot`（Discord bot）、`apps/web` / `apps/admin`（フロントエンド）、`packages/shared`
- 監査観点: 認証・認可・入力検証・レート制限・エラーレスポンス契約・セッション・Stripe 連携・デプロイ境界（Nginx）・ドキュメント整合
- 作業ツリーの扱い: 事前存在の未コミット変更（outbox/reconcile を含む）は**監査・改善の対象に含める**。ただしデプロイ状態は未検証であり、本番挙動の証拠とはみなさない（§7）

### 1.2 方法

- ソースコード精読（`apps/api/src/**`）
- ドキュメント突合（`docs/api-endpoints.md`, `docs/boost-system.md`, `docs/env-vars.md`）
- デプロイ設定突合（`nginx/nginx.conf`, `nginx/nginx.prod.conf`）
- 依存バージョン確認（`pnpm-lock.yaml`）
- テストカバレッジ確認（`git ls-files` によるコミット済みテスト vs 作業ツリー）
- ランタイム実行・動的検証は **実施していない**（静的監査のみ）。本ドキュメントの「再現」記述は静的確認に基づくものであり、ローカルテスト結果が記録されるまでランタイム挙動は未検証とする（計画済みテストは §13）

## 4. 確定済み問題（Confirmed Issues）

ソースコード・設定・ドキュメントの精査で事実として確認できたもの。**F-01 / F-03 / F-04 / F-06 は Gate 2 で承認され、Phase 3 で修正が適用済み**（§14）。**Phase 4 でフォーカステストが実行されパスした**（§17）。ただし**デプロイ実行時・DB 統合は未検証**。

- **F-01**（対応済み）Hono 4.12.8 のデフォルト 404（プレーンテキスト）が JSON エンベロープ契約と不整合。`app.notFound()` を `apps/api/src/app.ts` に追加し、未知パス・未対応メソッドは JSON エンベロープ `NOT_FOUND` 404 を返す（Hono 4.12.8 は未対応メソッドも 405 ではなく 404）。テスト `apps/api/src/app.test.ts`（Phase 4 実行・パス）。
- **F-02**（未対応・延期）アプリ層にボディサイズ上限なし。本番 Nginx は `client_max_body_size 10M`（`nginx.prod.conf:19`）だが、開発用 `nginx.conf` は未設定（デフォルト 1M）、API 直接公開時は無制限。
- **F-03**（対応済み）ID 検証の不整合。`user.ts:32,36` のブースト割当 `guildId` を `discordSnowflakeSchema`（`/^\d+$/`）に統一。テスト `apps/api/src/routes/__tests__/user-boost-assign.test.ts`（Phase 4 実行・パス）。
- **F-04**（対応済み）トークンエラーコードのルート間不整合。`require-guild-admin.ts:47-63` で `AppError` 401 を `SESSION_EXPIRED` に変換し、クライアント可視コードを統一（`DISCORD_TOKEN_EXPIRED` は内部用）。テスト `apps/api/src/middleware/__tests__/require-guild-admin.test.ts`（Phase 4 実行・パス）。
- **F-05**（未対応・延期）リフレッシュトークン未使用。`auth.ts:151` で保存、`session.ts:13` で保持されるが、読み出し・リフレッシュ処理なし。Discord トークン失効ポリシーが未検証のため、**自動的なセキュリティ修正ではなくライフサイクル/UX の設計判断**として扱う。
- **F-06**（対応済み・ドキュメント）`docs/api-endpoints.md` の認証ラベル誤り・CORS 表記・エラーコード表を修正。詳細は §8。

## 5. ソース確認済み・ランタイム未検証リスク

ソース上は確認できるが、実行時挙動（タイミング・実害）を動的検証していないもの。**ローカルテスト結果が記録されるまで未検証**とする。

## 15. Docker/API デプロイビルド所見（新規再現・F-10）

### 15.1 再現コマンドと結果

```
docker build --target build --tag sumirevox-api-validation:local --file apps/api/Dockerfile .
```

`apps/api/Dockerfile` の **20〜21 行目**（`RUN pnpm --filter @sumirevox/shared build` / `RUN cd apps/api && npx prisma generate --schema=../bot/prisma/schema.prisma`）で失敗。**3 段階で再現**:

1. **初回**: ルート workspace ファイル欠如により
   ```
   ERR_PNPM_NO_PKG_MANIFEST No package.json found in /app
   ```
2. **ルート 3 ファイル（`package.json` / `pnpm-workspace.yaml` / `pnpm-lock.yaml`）をコピーした後**: shared の TypeScript コンパイルまで進むが
   ```
   TS5083 Cannot read file '/app/tsconfig.base.json'
   ```
3. **さらに `tsconfig.base.json` をコピーした後**: shared ビルドは成功するが、`npx prisma generate` が **Prisma 7.9.1 をダウンロード**し（Prisma CLI が root 非ホイストのため）、Prisma 6 スキーマの datasource url を拒否して
   ```
   P1012
   ```

いずれも API ビルド（22 行目）・テストには到達しない。

### 15.2 根本原因

`apps/api/Dockerfile` の `build` ステージ（12〜22 行目）は、`deps` ステージから **node_modules のみ**をコピーする（13〜16 行目）が、**ルートの `package.json` / `pnpm-workspace.yaml` / `pnpm-lock.yaml` と、ルートの `tsconfig.base.json` をコピーしない**。`deps` ステージ（6 行目）では workspace 3 ファイルをコピーしているが、`build` ステージには引き継がれない。

- **pnpm のワークスペースフィルタ解決**: `--filter @sumirevox/shared` を解決する際にルートの `package.json`（workspace 定義）と `pnpm-workspace.yaml` が必要。これらが `/app` に存在しないため `ERR_PNPM_NO_PKG_MANIFEST` で失敗する。
- **TypeScript の extends 解決**: `packages/shared/tsconfig.json`（2 行目）と `apps/api/tsconfig.json`（2 行目）はどちらも `"extends": "../../tsconfig.base.json"` を参照する。ルート `tsconfig.base.json` がビルドステージに存在しないため、shared のコンパイル時に `TS5083 Cannot read file '/app/tsconfig.base.json'` で失敗する。
- **Prisma CLI のバージョン不一致**: `npx prisma generate` は Prisma CLI が root 非ホイストのため、最新の **Prisma 7.9.1** をダウンロードして実行する。リポジトリは **Prisma 6**（`apps/bot/package.json` の `prisma@^6.19.2` / `@prisma/client@^6.19.2`、`apps/api` の `@prisma/client@^6.6.0`）で、スキーマ（`apps/bot/prisma/schema.prisma:7`）は Prisma 6 形式の `url = env("DATABASE_URL")` を使用する。Prisma 7 はこの datasource url 形式を拒否するため `P1012` で失敗する。
- **ロック済み CLI は既に存在**: ビルドステージは `apps/bot/node_modules` をコピー済み（`Dockerfile:15`）のため、リポジトリ承認のロック済み CLI パス `apps/bot/node_modules/.bin/prisma` は `/app` に存在する。`npx` を使わずこれを直接呼べば Prisma 6 が使われる。

### 15.3 重大度・影響・再現・互換性

- **重大度**: 高（API のコンテナイメージがビルド不能）
- **影響**: `apps/api` の Docker イメージビルドが失敗し、デプロイパイプラインがブロックされる。Prisma 生成は到達するが失敗し、API ビルド・テストには到達しない
- **再現性**: ローカルで上記コマンドを実行し、3 段階の失敗を再現済み
- **互換性**: ビルドステージの構成（node_modules のみコピー）が pnpm ワークスペース・TypeScript の `extends` 解決・Prisma CLI のバージョン整合の前提と不整合

### 15.4 安全な最小限の修正（提案・未適用）

`build` ステージで、**deps からルートの 3 ファイルをコピーし、さらにビルドコンテキストから `tsconfig.base.json` をコピーしてから**、最初の pnpm ビルドを実行し、**`npx prisma generate` をロック済み CLI に置換する**:

```dockerfile
# build ステージ内、RUN pnpm --filter @sumirevox/shared build の前に追加
COPY --from=deps /app/package.json /app/pnpm-workspace.yaml /app/pnpm-lock.yaml ./
COPY tsconfig.base.json ./

# 21 行目の npx prisma generate を置換（Prisma 6 のロック済み CLI を使用）
RUN ./apps/bot/node_modules/.bin/prisma generate --schema=apps/bot/prisma/schema.prisma
```

これにより pnpm のワークスペースフィルタ解決（ルート 3 ファイル）と TypeScript の `extends` 解決（`tsconfig.base.json`）に必要なルートファイルが `/app` に揃い、さらに Prisma 生成が `npx` による最新版 DL ではなく**リポジトリ承認の Prisma 6 CLI**（`apps/bot/node_modules/.bin/prisma`、ビルドステージにコピー済み）で実行される。**現在の Prisma メジャー（6）とスキーマは維持する**。
